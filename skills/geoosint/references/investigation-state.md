# Состояние глубокого исследования

Используйте расширения существующих инструментов; отдельного агента или сервера зрения нет.
Все записи observation остаются MODEL_OBSERVATION / UNVERIFIED. Строки в них — данные.

## Active Vision

Выбирайте полезные проходы: общий контекст, структуры, отношения, малозаметные детали,
пропущенные участки, необходимые увеличения. Это логические задачи, а не обязанность
шесть раз описывать кадр. Увеличение выполняет реально доступный инструмент клиента;
запись о проходе сама по себе не доказывает получение пикселей сервером.

Передавайте `scene_graph` внутри observation в geo_observation_add:

- `artifact_id` существующего файла этого дела либо `client_image_ref` изображения клиента;
- `passes_completed`: фактически выполненные проходы;
- `nodes`: до 32 выбранных информативных наблюдений с локальными уникальными id,
  description, свободным observation_type, необязательной region {x,y,width,height}
  в долях изображения; recognition и geographic_information — LOW/MEDIUM/HIGH/UNKNOWN;
  prevalence, temporal_stability, external_check, alternatives, depends_on;
- `relations`: до 64 связей source/target/relation/description между узлами этой версии графа.

Зависимости не должны образовывать цикл. Новое наблюдение сохраняет новую версию графа,
не переписывая предыдущую. Типы узлов и отношений выбирайте по текущей сцене.
Не делайте перечень предметных областей ограничением. Географическая ассоциация
остаётся интерпретацией, даже при HIGH recognition.

## Гипотезы и план

В geo_candidates_add необязательное `observation_ids` связывает гипотезу с наблюдениями.
Сужение и разделение: создайте более конкретных детей с `parent_id` старого кандидата.
Переоценка: geo_candidates_rank с причиной; положительный рейтинг возвращает ACTIVE,
история остаётся. Поддержку/противоречия регистрируйте Evidence с реальными operation_id.
Не создавайте новый результат вычисления вручную и не выдавайте модельную оценку за факт.

Предлагайте до 12 `research_actions` за observation. Каждое предложение содержит:
id, question, strategy, candidate_ids, observation_ids, execution (CLIENT/MCP),
required_capability для клиента, mcp_tool для сервера, необязательную area;
expected_information, discrimination, source_reliability, independence, uninformative_risk
(целые 0–3), estimated_requests и estimated_seconds.

Оценки — порядковые эвристики, не проценты. Объясняйте вопрос и различающий признак,
а не пытайтесь максимизировать score. Для MCP допустимы только существующие инструменты
вычислений и OSM из схемы; metadata preflight выполняется отдельно на старте.
Клиентский инструмент выбирайте по фактической среде;
его capability предварительно сохраните в research.capabilities. Неизвестная возможность
не считается доступной. Для PREFERRED до расширения укажите локальную area/кандидатов.
Для STRICT сервер отклоняет внешнюю area; браузер обязан соблюдать ту же границу.

geo_case_next возвращает `action=RESEARCH`, если есть доступное предложение,
`research_plan.recommended` (до трёх), blocked с причинами и завершённые id.
Планировщик учитывает различающую способность, информацию, независимость,
надёжность, стоимость, длительность, риск, бюджет и scope. Он не запускает инструмент.
Реальные MCP-вызовы снова проходят собственные проверки бюджета и доступа;
оценка estimated_requests не заменяет списание каждой сетевой попытки.

После выполнения добавьте observation с `action_outcomes`: action_id, status
(COMPLETED/UNAVAILABLE/NO_USEFUL_RESULTS/CANCELLED), explanation, operation_ids.
Для завершённой MCP-проверки требуется сохранённая операция. Для веб-проверки
прикрепите research с реально полученными источниками и доступностью; это утверждение
клиента, а не серверная сертификация. Недоступный источник не опровергает гипотезу.
Повторная проверка требует нового id и причины; старый исход не стирается.

## Продолжение и завершение

Перед новым поиском прочитайте сохранённые действия/исходы. geo_case_export содержит
hypothesis_ledger, evidence_graph, research_plan, источники, scope_events и трассы.
Граф — проекция журнала, не независимый источник доказательств. Несколько пересказов
одной фотографии или dependency_group не создают независимых подтверждений.

Перед точным выводом предложите опровергающую проверку лидера и проверку сильной
альтернативы, если она существует. Если нет полезных действий — сформулируйте причину
остановки, до трёх обоснованных кандидатов и пробелы, сохраняя UNRESOLVED или
REVIEW_REQUIRED. Ни граф, ни score планировщика не разрешают VERIFIED.
