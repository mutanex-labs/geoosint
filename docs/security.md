# Авторизация и угрозы

Официальный MCP SDK обслуживает discovery, DCR, Authorization Code, PKCE S256,
проверку клиента, bearer middleware, scopes и 401 challenge. Прикладной OAuthProvider
хранит состояние в SQLite. Это собственный адаптер SDK, не отдельный аудит OAuth.

Одна приватная установка — один оператор, без регистрации пользователей. Для создания
hash: `geoosint password-hash`, интерактивный ввод, Argon2id. В репозитории и образе
нет настоящего пароля. Production без корректного hash, HTTPS BASE_URL и точного
allowlist redirect URI не стартует. `oauth-test` допускает HTTP только на loopback.
Отключённая авторизация допустима только в `local` с loopback; Compose local изолирует сеть.

## Жизненный цикл

Согласие: форма показывает клиента и callback, требует пароль и одноразовый pending
запрос. CSRF проверяется по Origin, HttpOnly SameSite cookie и токену формы.
HTML экранируется, CSP запрещает скрипты и embedding. Пароль не включается в URL.
Глобальные лимиты сдерживают подбор и не требуют Redis.

Коды живут 60 секунд, pending согласия — 5 минут. Access — 15 минут, refresh — 24 часа.
Случайные access/refresh генерируются `secrets`, в базе хранятся SHA-256 отпечатки.
При обновлении старый refresh становится недействительным, прежний access отзывается.
История использованных refresh хранится до истечения; повтор отзывает действующую семью.
Обмен одноразового кода и ротация выполняются в SQLite-транзакции. Параллельные
запросы не создают две действующие цепочки.

Проверяются resource/audience, срок, scope geoosint:use, субъект и владелец дела.
Каждый HTTP-запрос авторизуется заново, кеша положительной авторизации нет.
Stateless MCP не переносит чужую identity между соединениями. Известный case_id
не даёт доступа. Неизвестный/отозванный token — 401, недостаточный scope — 403.

DCR ограничен точными заранее разрешёнными callback URI и 100 клиентами.
Поддержаны confidential clients с client_secret_post/basic. CIMD и public client
authentication method none в этой версии отсутствуют. Клиентские секреты DCR хранятся
в приватной oauth.sqlite для проверки SDK; защищайте каталог и backup как секреты.

## Внешние запросы

Только фиксированный HTTPS Overpass endpoint. Разрешаются все DNS-адреса имени и
проверяется каждый; приватные, loopback и link-local запрещены. Запрос идёт к
проверенному IP с исходными Host/SNI, повторного DNS при connect нет. Редиректы
запрещены. Не используются proxy из окружения и пользовательские Authorization/Cookie.
Клиент не может передать произвольный URL или Overpass QL.

Host/Origin проверяются; отсутствие Origin допускается для нативного MCP-клиента.
Wildcard CORS SDK удаляется внешним boundary. Forwarded-заголовки не определяют
личность, issuer или публичный адрес; proxy_headers=False. BASE_URL задаётся оператором.

## Файлы и приватность

Оригиналы до 25 MiB, UUID-имена, контролируемый каталог, запрет symlink/path traversal,
формат по содержимому. Серверное чтение метаданных вынесено в дочерний Python-процесс
с тайм-аутом 5 секунд. Код файла не выполняется, пиксели не декодируются для чтения EXIF.
Парсер получает только разрешённый путь, не команду пользователя. Лимиты метаданных,
вершин/глубины XML и размеров изображения не снимаются.

Серийные номера не входят в allowlist ответа. Обычные логи приложения содержат
структурированные операционные поля, без текста дела, GPS, Authorization, cookie,
пароля и содержимого оригинала. Для библиотек форматтер сохраняет тип события без
сырого текста/traceback. Access log reverse proxy следует отключить для OAuth URL.

Удаление артефакта очищает приватные результаты и idempotency snapshots дела;
удаление дела удаляет оригиналы и зависимые SQL-записи. В backup данные остаются
до истечения срока хранения. SQLite secure_delete не гарантирует физическое стирание
на SSD, в WAL, снимках гипервизора и чужих backup.

Не предусмотрены скрытое отслеживание, публикация результатов или поиск адресов людей.
privacy_sensitive сохраняется; точные автоматические финальные результаты вообще
запрещены до независимой проверки сцены. Сервис предназначен для разрешённых материалов.

Остаточные риски: нет независимого security-аудита, лимиты одного процесса не являются
распределённой защитой, администратор файлового хранилища может менять данные,
нет гарантии атомарности SQL и удаления файла при внезапном сбое ОС.
